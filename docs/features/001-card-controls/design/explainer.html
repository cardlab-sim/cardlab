Card controls: freeze a card, cap spend by category

How CardLab will let a business admin freeze or unfreeze a card and set spend limits per category for a day, week or month, and how every purchase gets approved or declined against those rules. It ships with the full build, test and deploy loop.

Runs asOne ASP.NET Core host + React SPA
Stores inSQL Server (LocalDB / CI container / Azure SQL free)
Deployed toAzure App Service F1, £0 by design
Proven by40 acceptance checks, 5 property tests

What is being built, and why

CardLab is a fictional business credit card platform. This first feature gives the business account admin two controls over each card, and makes every purchase obey them.

In scope

  • Freeze / unfreeze a card. A frozen card declines every purchase.
  • Spend limits per category and per period (calendar day, Monday-to-Sunday week, calendar month, in UK time). At most one limit per category and period; all of them are checked.
  • Authorisation API that a card processor would call, plus a "simulate purchase" form in the admin UI.
  • Audit trail: every control change is an immutable event (who, when, what, old and new value).
  • Transaction history per card with outcome and reason.
  • Delivery loop: CI on every PR (build, xUnit, Playwright, CodeQL, ZAP, ticket key) and a deploy to one Azure environment, demo.

Out of scope

  • Real login (one seeded admin, "Sam Ellis", is the actor)
  • Cardholder self-service, card issuance
  • A real card network, merchant-code mapping
  • Multi-currency (GBP only), notifications
  • External ticket tracker, metrics dashboards
  • Deferred: a per-card total limit, idempotency keys, telemetry export

Architecture

One deployable. The host serves the admin UI as static files and the API from the same origin, so there is no CORS. The money logic sits in its own dependency-free project, which is the code the review tiers will later mark highest risk.

Authorising a purchase

Both the processor endpoint (POST /api/authorisations, by card number) and the admin's simulate form (POST /api/cards/{id}/simulate-purchase, by card id) run the same AuthorisationService. Only how the card is found differs, so the decision, the stored transaction and the log line are identical.

Example: a decline over the limit

POST /api/authorisations
{ "cardNumber": "9999000100000001", "amount": "30.00", "category": "fuel",
  "merchant": "Northway Fuel", "timestamp": "2026-10-25T00:30:00+01:00" }

200 OK
{ "outcome": "declined", "reason": "limit_exceeded", "transactionId": "…",
  "limits": [ { "category": "fuel", "period": "day", "limit": "50.00", "remaining": "20.00" } ] }

The card number is hashed (HMAC-SHA256 with a configured key) before anything is stored or logged. CardLab keeps only the hash and the last four digits; no screen, log, response or row ever holds 16 digits in a row, and tests scan all four for it.

Limit periods in UK time

A purchase falls in the period that contains the timestamp the caller sends. Periods are calendar day, Monday-to-Sunday week and calendar month in Europe/London, computed with .NET's built-in time zone support. Each period becomes a UTC range [start, end) and spend is the sum of approved purchases inside it.

Freezing a card and changing limits

Control changes go through CardControlsService under the same per-card lock, so a limit change and a purchase on the same card never interleave. Each real change writes the new state and one audit event together; a no-op (freezing a card that is already frozen, removing a limit that does not exist) writes nothing.

  1. Admin opens the card page and sets Fuel / Day to £80.00 (it was £50.00).
  2. PUT /api/cards/{id}/limits/fuel/day {"amount":"80.00"}. The amount is checked against £0.00 to £1,000,000.00; out of range returns 400 with nothing stored and no audit.
  3. Inside the lock: read current state, compute the change, upsert the limit and append the audit event limit_changed Fuel/Day/50.00 → Fuel/Day/80.00, then commit.
  4. One ControlChanged log event; the page shows the new limit and the audit list (newest first).

Lowering a limit below what was already spent is allowed: further spend in that category declines until the period resets. Removing a limit makes the category unlimited at once.

The admin UI

Two pages in a plain, light finance style with text-labelled status badges (never colour alone) and inline errors. Cards lists name, cardholder, last four and status. Card detail has the Freeze/Unfreeze button, spend limits with an inline add/edit form, the audit list, the simulate-purchase form with its result notice, and the transaction table. No modals.

The delivery loop

Heavy test runs never touch the deployed site: the free App Service plan has a daily 60 CPU-minute quota. Every PR runs the full suite against a copy of the app started inside CI; only one short smoke journey runs against demo after a deploy.

How to use it

Everyday commands

dotnet test tests/CardLab.Domain.Tests          # unit + property tests
dotnet test tests/CardLab.Integration.Tests     # needs LocalDB or CARDLAB_TEST_CONNECTION
npm test --prefix web                           # web unit tests
npm run e2e --prefix tests/e2e                  # full browser suite against a local host
npm run e2e --prefix tests/e2e -- --project smoke   # the deploy smoke (DEMO_URL)

One-off human setup before the deploy wave

Documented in docs/ops/azure-setup.md, written in the deploy PR:

  1. Create the Azure resource group.
  2. Create an app registration or managed identity with a federated credential for the repo's main branch and the demo environment; give it Contributor on the resource group.
  3. Set repo variables: AZURE_CLIENT_ID, AZURE_TENANT_ID, AZURE_SUBSCRIPTION_ID, AZURE_RESOURCE_GROUP, AZURE_WEBAPP_NAME, DEMO_URL (identifiers, not secrets).
  4. After the first Bicep run: create the SQL user for the web app's identity (one T-SQL script as the server's Entra admin).
  5. Set the CardLab__LookupKey app setting to a random 32-byte key (never in GitHub).
  6. Turn on branch protection for main requiring the CI, CodeQL and ticket-key checks.

  • Properties: spend never exceeds a limit; declines never change spend; remaining = limit − spend; every instant lands in exactly one day, week and month across DST; Money round-trips.
  • Contract suite: the same tests run against the in-memory store and the SQL store, so the fake cannot drift.
  • Privacy: a PAN scanner checks logs, API responses, table dumps and page text for any 16-digit run.
  • Performance targets (provisional until measured): decision ≤ 300 ms p95 locally with 1,000 stored transactions per card; simulate round trip ≤ 2 s on warm demo; warm-up ≤ 60 s.
  • Accessibility: axe reports zero critical or serious violations; J-1 and J-2 are walked by keyboard only.
  • All 40 acceptance checks map to named tests in §15.3 of the design doc; whole PR run target ≤ 12 min.

Glossary

Authorisation
The approve-or-decline decision for one purchase, stored as a transaction record.
PAN
The full 16-digit card number. CardLab never stores, logs or shows it.
Lookup hash
HMAC-SHA256 of the card number with a configured key; how CardLab finds a card from a processor call.
Period
Calendar day, Monday-to-Sunday week or calendar month in UK time.
Spend
Sum of approved purchases on a card in a category within a period.
Remaining
Limit minus spend after the decision, never below zero; returned with each decision.
Reason code
One of approved, card_frozen, limit_exceeded, card_not_found, invalid_request.
Audit event
Immutable record of a control change: actor, UTC time, card, action, old and new value.
Per-card lock
An exclusive SQL Server application lock on card:{id} held for one transaction.
Risk path
src/CardLab.Domain/: the money and limit code a later review-tier map will mark highest risk.
demo
The single deployed Azure environment.
Smoke journey
The one Playwright run against demo after a deploy: freeze, decline, unfreeze, approve.
Ticket key
CL-<issue number> in every PR title and body, checked by CI.
