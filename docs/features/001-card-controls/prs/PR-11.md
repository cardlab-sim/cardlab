# PR-11: Cross-path integration checks: limit changes, privacy, log events

## Goal
Verify the properties that span both API paths and need both PR-08 and PR-09 merged: lowering/removing a limit applies
at once to authorisations (AC-30, AC-31), no full card number anywhere after the journeys (AC-24), and exactly one
structured log event per authorisation and per real control change (AC-39). Test-only PR.

## Acceptance criteria covered (verbatim from requirements)
| AC | Covers | Given | When | Then |
|----|--------|-------|------|------|
| AC-24 | NFR-1 | the journeys J-1..J-3 executed, including an unknown-card request | application logs, audit events, API responses, stored transaction and audit rows and UI screens are inspected | no full card number (16 consecutive digits) appears anywhere; only the last four digits do |
| AC-30 | R-13, R-4 | a card with Fuel / day / £50.00 and £40.00 approved Fuel spend today | the admin lowers the limit to £30.00 and then a request for £0.01 Fuel arrives today | the limit is £30.00, the earlier £40.00 of transactions are unchanged, and the request is declined with `limit_exceeded` with remaining £0.00 |
| AC-31 | R-13, R-4 | the card of AC-30 | the admin removes the Fuel/day limit and a request for £1,000.00 Fuel arrives today | the response is `approved` |
| AC-39 | NFR-7, NFR-1 | the journeys J-1..J-3 executed | the application log output is inspected | each authorisation and each control change has exactly one structured log event with the fields of NFR-7, and none contains a full card number |

## Design context (excerpts)
**NFR-1 / AC-24:** no full card number (16 consecutive digits) in any log line, error message, audit event, stored record
(other than the lookup hash), API response or UI screen; at most the last four. The PAN enters only through
`POST /api/authorisations`; responses, ProblemDetails, logs and rows must be scanned.
**NFR-7 / AC-39 (DEC-12, §12):** events `AuthorisationDecided` (fields `CardId`, `LastFour`, `Category`, `Amount`,
`Outcome`, `Reason`, `DurationMs`) and `ControlChanged` (`ActorId`, `ActorName`, `CardId`, `LastFour`, `Action`),
exactly one per decision / real change, emitted by the services (so the simulate and processor paths log identically).
For invalid and unknown-card requests `CardId`/`LastFour` are `"-"` (PR-08's choice). No-ops (freeze a frozen card,
remove an absent limit) log nothing.
**R-13:** limit changes apply immediately; lowering below existing spend is allowed and leaves history untouched; removing
makes the category unlimited at once.
