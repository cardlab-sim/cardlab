# PR-08: Authorisation service and endpoints (processor and simulate)

## Goal
Deliver J-3 end to end on the server: `AuthorisationService` (validate → resolve card → decide inside the per-card lock
→ store → log once) and its two HTTP entry points, `POST /api/authorisations` (card number) and
`POST /api/cards/{id}/simulate-purchase` (card id), with DEC-14 status codes. Proven with unit tests on fakes and
integration tests on SQL Server, including the 10-way concurrency test and the latency budget.

## Design context (excerpts)
**Flow (design §8).** `AuthoriseAsync(raw)`: start a `Stopwatch` (`Stopwatch.GetTimestamp()`); `TransactionRules.Validate`
→ on failure return `Decision(Declined, InvalidRequest, [])` with the problems, store nothing and do not call the lookup.
Else `lookup.Compute(digits)` → `store.FindByLookupAsync` → null → `Decision(Declined, CardNotFound, [])`, store nothing.
Else `store.WithCardLockAsync(cardId, async w => { state = await w.GetStateAsync(); limits = state.Limits where Category
== request category; for each: range = PeriodCalendar.RangeContaining(occurredAt, limit.Period); spend = await
w.SumApprovedSpendAsync(category, range); decision = AuthorisationDecider.Decide(state.Status, limitsWithSpend, amount);
id = w.AppendTransaction(new NewTransaction(amount, category, merchant, occurredAt, clock.UtcNow, decision.Outcome,
decision.Reason)); })`. Then log exactly one `CardLabEvents.AuthorisationDecided(logger, cardId, lastFour, category,
amount, outcome, reason, durationMs)` with wire names and `Money.ToString()`; use `"-"` for card id / last four when no card
was resolved and for category / amount when they were invalid (never log raw request text: it could contain a card
number). The period comes from the request timestamp, never the clock (R-13, AC-33). `AuthoriseByCardIdAsync(id,
purchase)`: `TransactionRules.ValidatePurchase(purchase, clock.UtcNow)`, then the same locked path with `id`; a null
state means unknown id → `CardNotFound`, nothing stored. `CardLockTimeoutException` propagates (PR-09 maps it to 503).

**HTTP (DEC-14, §7).** Both endpoints return `DecisionDto {outcome, reason, transactionId, limits:[{category, period,
limit, remaining}], problems:[{field, message}]}` (wire names via `WireNames`, amounts via `Money.ToString()`), status
200 for approved / card_frozen / limit_exceeded, 404 for card_not_found, 400 for invalid_request; use
`TypedResults.Json(dto, statusCode: ...)`. The body shape is the same in all cases; the card number is never echoed.
Request bodies bind to the domain records `AuthorisationRequest` / `SimulatedPurchase` (all fields strings).

## Harness to use

## Planner decisions (PLANNER-DECISION)
- `problems` is always present in the decision body (empty unless `invalid_request`); requests whose JSON types do not
  bind (e.g. `amount` as a number) get the framework's 400 ProblemDetails rather than a decision body.
- An `AuthorisationDecided` event is also logged for invalid and unknown-card requests, with `"-"` placeholders, so
  "every authorisation" in NFR-7 holds for all five reasons.
