# PR-04: Domain decision core: periods, validation, decider, properties

## Goal
Implement the pure money/limit decision path: Europe/London period ranges, request validation, the approve/decline
decider, PAN-masking `ToString`, and the FsCheck property suite. This is the heart of R-5, R-11 and R-13 and the
high-risk path: strictest review, property-based tests (NFR-2).

## Design context (excerpts)
**PeriodCalendar (DEC-15).** Convert the instant to Europe/London (`TimeZoneInfo.FindSystemTimeZoneById("Europe/London")`,
cached in a static field), take the local `DateOnly`, derive the first local day (day: itself; week: the Monday on or
before it, i.e. subtract `((int)dow + 6) % 7` days; month: day 1), and convert local 00:00 of that day and of the next
period's first day to UTC with `TimeZoneInfo.ConvertTimeToUtc(new DateTime(date, TimeOnly.MinValue, DateTimeKind.Unspecified), tz)`.
Return offsets of zero. In Europe/London the DST gap/overlap is at 01:00-02:00 local, so local midnight is never invalid
or ambiguous; the property tests prove tiling anyway. 2026 changes: 2026-03-29T01:00Z (23-hour day) and
2026-10-25T01:00Z (25-hour day).

**AuthorisationDecider (§8).** Order: frozen → `Declined/CardFrozen`; else if any limit has `spend + amount > limit` →
`Declined/LimitExceeded` (equal is approved; evaluate every limit); else `Approved/Approved`. No limits = unlimited.
`Limits` = one `LimitRemaining` per input, input order; remaining = `limit - (spend + amount)` when approved, `limit - spend`
when declined, floored at zero by `Money -`.

**TransactionRules (R-7, R-11, §9).** See the doc comment in `TransactionRules.cs`. Report every problem (one per field),
fields `cardNumber`, `amount`, `category`, `merchant`, `timestamp`; messages in English (UK), never echoing the submitted
card number. Card number: exactly 16 ASCII digits `[0-9]{16}`. Amount: `WireNames.TryParseAmount` → `Money.TryFromDecimal`
(≤ 2 dp, ≥ 0) → `MoneyBounds.IsValidTransactionAmount`. Category: `WireNames.TryParseCategory`. Merchant: trimmed,
1..200 chars. Timestamp: `DateTimeOffset.TryParse(text, CultureInfo.InvariantCulture, DateTimeStyles.None, out t)` AND the
text must carry an explicit offset (`Z` or `±hh:mm` at the end, regex `(Z|[+-]\d{2}:\d{2})$`); truncate to whole seconds
(`t.AddTicks(-(t.Ticks % TimeSpan.TicksPerSecond))`), keep the offset. `ValidatePurchase` uses `defaultOccurredAt` when the
timestamp is null or empty and has no card-number rule.

**ToString masking (NFR-1, §10):** `AuthorisationRequest` and `ValidatedAuthorisation` print the card number as
`************` + last four (or `<missing>` / `<invalid>` if it has fewer than 4 chars) and the other fields as is.

**Properties (DEC-7, AC-25)** with FsCheck.Xunit.v3 3.3.4: `[Property(Arbitrary = new[] { typeof(CardLabArbitraries) })]`;
C# generator API in `FsCheck.Fluent` (`Gen.Choose`, `.Select`, `.Where`, `Arb.From(gen)`); arbitraries are
`public static Arbitrary<T> Name()` methods. Default 100 cases each; keep each property ≤ 1 s. Assert with `bool` return
or `.ToProperty()`; FsCheck prints the seed on failure.

## Planner decisions (PLANNER-DECISION)
- `TransactionRules.Validate` returns `Result<ValidatedAuthorisation, IReadOnlyList<ValidationProblem>>` (design:
  `Result<..., Reason>`); the reason is always `invalid_request`, and the problem list feeds DEC-14's `problems`.
- `ValidatePurchase` (simulate path, no card number) is an addition the design implies but does not name.
- Validation details not fixed by the design: card number exactly 16 digits with no separators; timestamp must carry an
  explicit offset; merchant 1..200 chars after trimming; wire names exact lower case.
