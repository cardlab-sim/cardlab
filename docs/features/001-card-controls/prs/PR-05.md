# PR-05: Card controls: freeze, unfreeze and limit changes with audit

## Goal
Implement the control-change rules (`CardControls`) and the admin application service (`CardControlsService`):
freeze/unfreeze with no-op detection, set/replace/remove limits, one immutable audit event per real change, and one
`ControlChanged` log event per real change, all inside the per-card lock. Unit-tested with the in-memory store; the HTTP
surface is PR-09.

## Acceptance criteria covered (verbatim from requirements)
| AC | Covers | Given | When | Then |
|----|--------|-------|------|------|
| AC-1 | R-1, R-6 | an active card | the admin freezes it | the card's status is frozen and one audit event exists: action freeze, actor = the seeded admin, UTC time, card last four, old status active, new status frozen |
| AC-2 | R-1, R-6 | a frozen card | the admin freezes it again | the status stays frozen and no new audit event is created |
| AC-3 | R-2, R-6 | a frozen card | the admin unfreezes it | the status is active and one audit event exists with action unfreeze, old frozen, new active |
| AC-6 | R-4, R-6 | a card with no limits | the admin sets a limit Fuel / day / £50.00 | the limit is listed on the card and one audit event exists: action limit set, new value Fuel day £50.00 |
| AC-7 | R-4, R-6 | a card with Fuel / day / £50.00 | the admin sets Fuel / day / £80.00 | the card has exactly one Fuel/day limit, of £80.00, and an audit event exists: action limit changed, old £50.00, new £80.00 |
| AC-8 | R-4, R-6 | a card with Fuel / day / £80.00 | the admin removes it | the card has no Fuel/day limit and an audit event exists: action limit removed, old £80.00 |
| AC-9 | R-4, R-11 | any card | the admin sets a limit of -£1.00, £1,000,000.01 or £10.005 | the request is rejected, no limit is created or changed and no audit event is written |
| AC-40 | R-2, R-6 | an active (not frozen) card | the admin unfreezes it | the status stays active and no new audit event is created |

The same ACs are checked through the API in PR-09 (T-I-1, T-I-3).

## Design context (excerpts)
**Rules (design §5, R-1, R-2, R-4, R-6).** `CardControls` is pure: `Freeze(Active)` → `Frozen` + `AuditEvent(card, actor,
nowUtc, Freeze, "Active", "Frozen")`; `Freeze(Frozen)` → null. `Unfreeze(Frozen)` → `Active` + `Unfreeze` ("Frozen" →
"Active"); `Unfreeze(Active)` → null. `SetLimit(null, requested)` → `LimitSet` (old null, new value);
`SetLimit(existing, requested)` → `LimitChanged` (old, new) — always a change. `RemoveLimit(existing)` → `LimitRemoved`
(old value, new null); `RemoveLimit(null)` → null. Value format: `"{Category}/{Period}/{Money}"` with enum names, e.g.
`"Fuel/Day/50.00"`; status values `"Active"`/`"Frozen"`.

**Service flow (design §8, second sequence).** `SetLimitAsync`: first `Money.TryFromDecimal(amount)` and
`MoneyBounds.IsValidLimitAmount` → else `Fail(InvalidAmount)` without touching the store (AC-9). Then
`store.WithCardLockAsync(cardId, async w => { state = await w.GetStateAsync(); if null → CardNotFound; change =
CardControls.SetLimit(existing in state.Limits for (category, period), requested, state.Card, actor.Current,
clock.UtcNow); w.UpsertLimit(change.NewState); w.AppendAudit(change.Event); })`. After the lock returns with a real
change, log once: `CardLabEvents.ControlChanged(logger, actor.Id.ToString(), actor.Name, cardId.Value.ToString(),
lastFour, WireNames.ToWire(action))`. Freeze/Unfreeze: same pattern with `w.SetStatus`; return the status after the call
(also on no-op). `RemoveLimitAsync`: `Ok(true)` when removed, `Ok(false)` for a no-op. Unknown card → `Fail(CardNotFound)`
for all four operations; nothing written. Log after the unit of work commits (never log a change that rolled back).
