## Judgement on the points the orchestrator asked about
- **Retry bounds** (`DatabaseSetup.cs:38-52`). The filter `catch (SqlException) when (clock.Elapsed + RetryDelay < RetryWindow)` retries only `SqlException`. `DependencyInjection.cs:36` uses plain `UseSqlServer` with no EF execution strategy, so nothing wraps the exception in `RetryLimitExceededException`. The delay is 5 s. The last retry starts no later than 120 s. When the filter is false the exception is not caught, so the **original** `SqlException` propagates with its stack and stops the host as design §9 requires. Cancellation: `ct` reaches `MigrateAsync`, `EnsureSeedAsync` and `Task.Delay`, so it is honoured (see nit N-1 for one edge case). Worst case on `demo`: about 115 s plus one attempt (up to `Connect Timeout=60`). That stays inside the Linux App Service container start limit (230 s; `main.bicep:32,45` is Linux), and Program.cs does not listen before initialisation, so no ANCM 120 s limit applies.
- **No connection details**. The message is a fixed `LoggerMessage.Define` text, and the exception is passed as `null`. I observed this on the host run above. EF Core's own `CommandError` log does include `CREATE DATABASE [<db>]` (N-2). That is the database name, not connection details, and the code did this before the PR too.
- **BuildInfo**. `BuildInfo.Resolve` (`BuildInfo.cs:22-35`) is the old `HealthEndpoints.ResolveCommit` copied without change, and the T-I-10 theory now points at it (`HealthTests.cs:46`). Health behaviour did not change: it still uses `CardLabOptions.Commit` plus the entry-assembly informational version. Telemetry has one deliberate improvement: a whitespace-only `CardLab:Commit` now falls back instead of being stamped as-is. That matches the health rule.
- **deploy.yml** (`:78-80`). The connection string gains exactly `;Connect Timeout=60;Connect Retry Count=3;Connect Retry Interval=10`, which are valid SqlClient keywords inside their ranges. `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true` is added to the same merge-semantics `--settings` list, so `CardLab__LookupKey` still survives. actionlint is clean. Spoofing risk: forwarded headers with known proxies cleared take only the right-most `X-Forwarded-For` hop (ForwardLimit 1), which is the one App Service's front end sets. The app does not use `RemoteIpAddress` for any decision.
- **Ordering (F-3)**. `SqlCardStore.cs:51` and `InMemoryCardStore.cs:88` both apply `OrderBy(Category).ThenBy(Period)` after mapping. The enum order is Travel < Fuel and Day < Week, so the contract literal `[Travel/Day, Fuel/Day, Fuel/Week]` (`CardStoreContractTests.cs:113`) is derived by hand and is a real reordering of the upsert order. The orchestrator ran the mutations: removing the order fails T-U-21 and T-I-12.
- **Behaviour change beyond the findings**: none found.

**Nits (no action required):**
- **N-1:** `DatabaseSetup.cs:47`. If `ct` fires during a SqlClient call, SqlClient can throw `SqlException` ("Operation cancelled by user") rather than `OperationCanceledException`. That logs one spurious "not ready" warning before `Task.Delay` throws. Adding `!ct.IsCancellationRequested &&` to the filter avoids it.
- **N-2:** During a resume, EF Core logs `Failed executing DbCommand … CREATE DATABASE [cardlab]` at **Error** on every attempt. Its `Exists` check reports "missing" for an unavailable database, so `MigrateAsync` tries to create it. This is harmless (the create fails with "already exists", which is a `SqlException` and is retried) but noisy. Leave it as is unless alerts are added later.
- **N-3:** `HealthEndpoints.cs:30-32` repeats the entry-assembly lookup that `BuildInfo.Commit` already does. Something like `BuildInfo.Resolve(options.Value.Commit, BuildInfo.InformationalVersion)` would remove the duplicate.
- **N-4:** `StartupRetryTests.cs:35-47` copies the provider setup from `SqlTestDatabase.InitializeAsync`. A shared harness helper would fit a later harness-owning PR.
