# PR-09 review: Admin API: card endpoints, health, test reset, security headers

## Verdict: CHANGES

1 blocker, 2 major (one of them `upstream:design`), 3 minor, plus nits. The eight card handlers are thin and follow §7 and
DEC-19: wire names come from `WireNames`, amounts from `Money.ToString()`, 404s are ProblemDetails "Card not found",
validation errors use `ValidationProblem`, and nothing is stored on a 400. Reset and the test-endpoint flag follow DEC-16.
The exception handler follows §9 and never echoes exception text. The blocker is a cross-PR seam: when `CardLab:Commit` is
unset (the case on `demo` since BUG-001), health reports `1.0.0+<sha>`, but `deploy.yml` waits for the bare `<sha>`, so every
deploy's health wait will time out. No blocker fix needs my judgement to re-check (no `recheck`); each one has a mechanical
check below.

## Coder deviations: judgement
- **Row 9 via taking a test database OFFLINE under a running API (~15 s):** accepted. The test proves the real handler maps `false` to 503 `{commit, database:"unreachable"}` through the host. It runs on its own `ApiFactory`/database and restores `ONLINE` in `finally`. The direct `DatabaseProbe` check against `127.0.0.1,1` covers the brief's "constructed directly" half. The cost (~15 s) fits the §15.6 budget. A public static helper would not have been an alternative for the endpoint mapping itself.
- **Reset and error-mapping tests not red-first (mutation substitute):** accepted. Both tests can fail: dropping the limit delete kills T-I-15, and dropping the wrapper mapping kills T-I-21. This is a process deviation only.
- **`SqlException` via `RuntimeHelpers.GetUninitializedObject`:** accepted. The handler only type-tests it, and SqlClient exposes no constructor. If the handler ever inspects `Number`/`Errors` (e.g. for the 1205 nit), this fixture must become a real `SqlException` from a failed connection.
- **503 mapping:** matches §9 and the brief. `CardLockTimeoutException` → "Try again"; `SqlException` and `DbUpdateException`/`InvalidOperationException` wrapping one → "Service unavailable"; other types → false. The tests use a secret containing a 16-digit run, and it never reaches the body. See m-2 for the one framework type worth adding.
- **Health commit order (`CardLab:Commit` → informational version → "unknown"):** the order is right, but the fallback value has the wrong shape. See B-1.

## Requested checks
- **Reset absent without the flag:** confirmed. Program.cs maps `MapTestEndpoints` only when `CardLab:TestEndpoints` is true. `appsettings.json` has `false`, and `deploy.yml` never sets it. T-I-15 overrides the Development value to `false` and asserts 404 with state unchanged (frozen card and 1 audit event kept). The probe got 404 ProblemDetails for POST, GET, case variants and a trailing slash.
- **CSP/headers vs ZAP baseline:** CSP has `default-src`, `script-src` and `style-src` all `'self'`, with no `unsafe-inline`/`unsafe-eval`. The no-fallback directives `frame-ancestors 'none'`, `form-action 'self'` and `base-uri 'self'` are all present. XFO, nosniff, Referrer-Policy, Permissions-Policy, COOP and CORP are present, and `no-store` is set on `/api/*`. All of these are applied via `OnStarting`, so they also cover 404/500/static responses; `UseSecurityHeaders` runs before `UseStaticFiles`. HSTS is not expected on the CI-local HTTP run. The one predictable alert is 90004 (M-1).
- **Card numbers in responses:** PR-09's DTOs carry `lastFour` only. Validation problems name fields, not inputs. The 404s and the 503 contain only titles, and the exception messages are never written. `PanScanner` runs over the list, detail, 404, transaction and audit bodies. The only path a 16-digit run can still take into a response is the processor-supplied `merchant` text (M-2, `upstream:design`).
