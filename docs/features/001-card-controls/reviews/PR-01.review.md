## Coder notes checked
- **CardBuilder uses a private `FakeCardNumberLookup`**: accepted. The hash is the same as `Instance` would give (both are unkeyed SHA-256), and this stops builders from inflating `Instance.Calls`. It differs from the brief's wording ("lookup via `FakeCardNumberLookup.Instance`"), but the doc comment states it. The shared counter is still racy (m-3).
- **5 s lock cap → `CardLockTimeoutException`; writes for an unknown card throw**: accepted. Both match the `ICardStore.WithCardLockAsync` doc and DEC-4. An accidental nested lock on the same card now fails loudly after 5 s instead of hanging. Throwing on writes for an unknown card is stricter than the contract and SQL behaves the same way in effect (an FK failure at save). Services check for a null state first.
- **Concurrency test counts with `SumApprovedSpendAsync` over £1.00 rows and `Task.Yield`**: sound for the in-memory store (the clean no-lock mutation kills it). Against SQL it fails for the wrong reason (B-2).
- **Subtraction floors by comparison instead of `Max`**: equivalent, accepted.
- **Contract tests never went red**: mutations show they fail meaningfully against the in-memory store. C-5 will also catch a real SQL bug (EF change-tracker state left over after a rollback). Two of them, C-7 and C-10, would fail against the planned SqlCardStore for reasons the contract does not cover (B-1, B-2).

## Spec check (AC-9, value level)
`-1.00` and `10.005` are rejected by `TryFromDecimal` (`Money.cs:30-41`). `1000000.01` is rejected by `IsValidLimitAmount` (`MoneyBounds.cs:17`), and `0.00` is accepted as a limit. `0.00` is rejected as a transaction and both bounds are inclusive (`MoneyBounds.cs:12`). Wire names and the amount syntax match design §7. `LookupHash` matches DEC-8 and the brief. Nothing from the design was lost in the brief excerpt.
