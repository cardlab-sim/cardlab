# PR-02: Payment test harness: in-memory store, scriptable bank, contract suites

## Goal
Give every later payment PR its test doubles and the two contract suites that keep the doubles honest (design §15.2):
the payment half of `InMemoryCardStore` (reads + `IPaymentWriter` with copy-on-commit and the two uniqueness rules),
the scriptable `FakeBank`, `FakePaymentReferences`, the `PaymentStoreContractTests` and
`CurrentAccountBankContractTests` suites (bodies written here, run against the in-memory doubles; PR-05 runs them against
SQL unchanged), and the `PanScanner` account-number pattern. Test-only PR (reviewer `pr-light`).

## Acceptance criteria covered (verbatim from requirements)
| AC | Covers | Given | When | Then |

## Design context (excerpts)
**Ports (PR-00, complete).** `ICardStore` gained `GetLinkedAccountAsync`, `GetBalanceAsync(CardId) → CardBalance(ApprovedPurchases,
CompletedPayments, Owed)`, `GetPaymentRecordAsync(reference)`, `ListPaymentRecordsAsync(CardId)` (newest first by quote time,
incl. open and refused quotes), `ListActivityAsync(CardId, take)` (purchases by `DecidedAtUtc`, payments by `CreatedAtUtc`,
merged newest first; quotes without a payment are not activity). `ICardWriter.Payments : IPaymentWriter` with
`SumApprovedPurchasesAsync`, `SumCompletedPaymentsAsync`, `GetQuoteAsync` (null for another card's reference),
`GetPendingPaymentAsync`, `AppendQuote`, `SetQuoteStatus` (only Status/RefusedAt/RefusalReason/BalanceAtRefusal change),
`CreatePayment` (Pending), `SettlePayment`, `AppendEvent`. Read the doc comments in `src/CardLab.Domain/Ports/ICardStore.cs`
and `src/CardLab.Domain/Ports/ICurrentAccountBank.cs`; they are the contract.

**Store invariants the SQL schema enforces and the in-memory store must mirror (design §6):** one payment per reference
(unique `Payment.Reference`); at most one Pending payment per card (`UX_Payment_OnePending`); violations make the unit of
work throw on commit and store nothing. Sums count committed rows; in-memory follows the 001 rule "do not rely on sums
including rows appended in the same unit of work". Balance = approved purchases − completed payments, floored at £0.00
(implement the floor with `Money -`; do not call `BalanceRules`, which is PR-01's and may still be a stub).

**Bank port contract (design §5):** a reference the bank has seen is never applied twice (repeat returns the recorded
outcome); a debit above the available balance is refused InsufficientFunds; status by reference answers Completed
(with debit time) / Refused(reason) / NotReceived; calls may never return (caller's token is the budget).
**FakeBank scripts (design §15.2, PLANNER-DECISION):** one-shot `NextDebit(outcome)` (Completed applies the debit and
posts an entry; Refused moves nothing), `Hang(debitApplied)` (optionally applies, then throws `OperationCanceledException`
immediately: it stands for "the budget fired", so unit tests never wait), `FailNext(error)`, `NextStatus(outcome)`,
`HangStatus()`, `HoldDebitsUntil(Task)` (AC-10 gate). Posting/debit times come from the injected `IClock`.

**PanScanner (design §10):** the second pattern is the literal seeded account number `Seed.LinkedAccountNumber`
("51907731"), not "8+ digits" (GUIDs such as the BankAccountRef contain long digit runs).

## Harness to use
Contract subclasses: `CreateStoreAsync(cards, account)` → `new InMemoryCardStore(cards).WithLinkedAccount(account)`;
`OpenStoreAsync(seeded)` → the same instance. `CreateBankAsync(ref, lastFour, opening)` →
`new FakeBank(new FakeClock(t0), ref, lastFour, opening)`. Ids from counters (never random), like the 001 store.
