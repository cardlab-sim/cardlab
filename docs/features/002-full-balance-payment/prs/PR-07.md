# PR-07: Admin payment visibility: balance, activity, payments list and record (API + web)

## Goal
A vertical slice for the admin: `GET /api/cards/{id}` gains `balanceOwed`; new `GET /api/cards/{id}/activity`,
`GET /api/cards/{id}/payments` and `GET /api/cards/{id}/payments/{reference}` (the AC-20 compliance record); the admin
card detail shows the balance, an Activity table (purchases and payments) replacing Transactions, a Payments section,
and runs the automatic status check for a pending payment (DEC-13); a new read-only payment record page. Integration
tests arrange payments through `PaymentService` from a host scope, so this PR does not wait for PR-06.

## Acceptance criteria covered (verbatim from requirements)
| AC | Covers | Given | When | Then |
|----|--------|-------|------|------|
| AC-1 | R-1 | a card with approved purchases £120.00 and £30.50, a declined purchase £500.00 and no payments | the cardholder view and the admin card detail are opened | both show a balance owed of £150.50 |
| AC-2 | R-1, R-13 | the card of AC-1 after a completed payment of £150.50 | the balance is read | it is £0.00; the card's history lists the payment as a payment (not a purchase) with state completed |
| AC-20 | R-14 | a payment in each state (completed, failed, pending) and a refused reference | the admin opens each record | it shows the amount, fee, total, execution-time statement and accounts exactly as displayed on the review screen (fields and rendered wording with its version), the acceptance time, the acting cardholder and the authority basis, the reference, every confirm attempt with its time, each bank outcome with its time, the balance owed immediately before and immediately after the settled amount was applied where settled, and whether the outcome was simulated; after a status check, a repeated confirm or a restart the shown-and-accepted part is unchanged |
| AC-34 | R-11 | a pending payment whose debit the bank has since applied | the cardholder view (or the admin card detail) is opened, without pressing *Check status* | the payment is completed, the balance is £0.00, and the payment's effective time is the bank's reported debit time |

## Design context (excerpts)
**API (design §7; routes complete in PR-00, handlers yours).**
| Method & path | Response |
|---|---|
| `GET /api/cards/{id}` | `200 CardDetailDto {..., balanceOwed}`: pass `BalanceOwed = (await store.GetBalanceAsync(id)).Owed.ToString()` |
| `GET /api/cards/{id}/activity?take=` | `200 ActivityDto[]` newest first (`store.ListActivityAsync(id, take ?? int.MaxValue)`, `PaymentDtoMapper.ToDto`); `404` unknown card |
| `GET /api/cards/{id}/payments` | `200 PaymentListItemDto[]` newest first (`ListPaymentRecordsAsync` → `PaymentDtoMapper.ToListItem`), incl. open and refused; `404` |
| `GET /api/cards/{id}/payments/{reference}` | `200 PaymentRecordDto` (`GetPaymentRecordAsync` → `PaymentDtoMapper.ToDto`); `404` for unknown card, malformed reference (`PaymentReference.TryParse`), unknown reference or a record whose `Quote.Card` is another card |
`/transactions` stays unchanged (DEC-12). Acceptance time in the record = payment creation, else the first refused
confirm, else null (PLANNER-DECISION, implemented in `PaymentDtoMapper`).

**Admin UI (design §4.1).** Card detail heading gains "Balance owed £150.50". The 001 Transactions section becomes
**Activity** (heading "Activity"; keep the table caption "Transaction history" so 001's AC-22/AC-38 page objects keep
working): columns Time (London), Type (badge Purchase/Payment), Description (merchant, or a link "Payment PAY-…" to the
record), Category (purchases; "—" for payments), Amount, Outcome (badge Approved/Declined or Pending/Completed/Failed),
Reason (purchase reason label; "origin: smoke" badge for smoke payments). New **Payments** section: every reference newest
first with link, amount, created time, status, state and origin badges. **Auto check (DEC-13):** when the payments list
contains a `pending` payment, call `checkPayment(cardId, reference)` once, then refetch card, activity and payments.
**Payment record page** `/cards/:id/payments/:reference`: sections "What the cardholder saw" (heading, lines verbatim,
button text, "Wording version v1"), "Acceptance" (time, actor name and kind, authority basis, origin), "Payment" (state,
amounts, balances before/after, effective/settled/bank debit times, "Simulated outcome" when simulated, failure reason) or
the refusal (reason, balance at refusal), "Events" table (time, kind, from → to, detail, simulated). 404 → Notice
"Payment not found" with a link back. 001 UI rules apply (tokens only, text badges, no modals, keyboard).
The contracts are also in the doc comments of `pages/PaymentRecordPage.tsx` and `pages/cardDetail/paymentSections.tsx`.

**001 E2E compatibility:** `tests/e2e/src/pages/CardDetailPage.ts` (yours) reads rows of the table named "Transaction
history" expecting six cells (time, merchant, category, amount, outcome, reason). Update `transactions()` to read the
Activity table and return only purchase rows with the same fields, so `freeze.spec.ts`, `simulate.spec.ts` and
`formatting.spec.ts` stay green unchanged. Do not change other methods' accessible names.
