# PR-03: Cardholder web journey: view, review, receipt, fake-bank panel, API clients

## Goal
Build the cardholder area of the SPA (DEC-11): the no-login cardholder view `/cardholder/:id`, the one review screen
`/cardholder/:id/pay`, the receipt `/cardholder/:id/payments/:reference`, the labelled fake-bank panel, the cardholder
page frame, the "Cardholder view" link on the card list, and both API client implementations for all ten 002 methods
(`HttpApiClient` to the real routes, `FakeApiClient` simulating the flow for every web unit test, including PR-07's).
Runs on `FakeApiClient`; the server half lands in PR-06.

## Design context (excerpts)
**Wording (DEC-10):** every customer-facing payment string (W-1..W-10) comes from the server (`quote.wording`,
`receipt.message`, `view.availabilityMessage`, 409 `problem.message`) and is shown verbatim. The SPA never builds them.
`FakeApiClient` must return the exact §17 strings so page tests are realistic; copy them from
`docs/features/002-full-balance-payment/01-requirements.md` §17 into the fake (test support, not UI).

**Routes (PR-00 `App.tsx`, complete):** `/cardholder/:id` (index), `/cardholder/:id/pay`, `/cardholder/:id/payments/:reference`,
all inside `<CardholderShell/>` (layout route rendering `<Outlet/>`).

**Layout and UI rules (design §4.1, checkable):** single column, max-width 720 px, usable at 768 px; 001 rules (contrast
≥ 4.5:1, keyboard, text badges never colour alone, no modals, no icons, tokens only, buttons ≥ 44 px tall and ≥ 8 px
apart, `prefers-reduced-motion`). Cardholder header: "CardLab", "Brightline Supplies Ltd", the cardholder's name (not
"Sam Ellis") and the label "Cardholder view". Page contracts are in the doc comments of the stubs:
`CardholderShell.tsx`, `CardholderViewPage.tsx`, `ReviewPage.tsx`, `ReceiptPage.tsx`, `FakeBankPanel.tsx` (read them;
they fix headings, region names, button names and DOM order that PR-08's page objects rely on). Key points:
- View: Balance section (32 px tabular figure; button "Pay full balance" or the availability message; "Check status"
  for `payment_pending`); Pending payment Notice (W-5, role="status", "Check status"); Linked current account; Recent
  card activity table (≤ 10); Current account recent activity table (≤ 10); last in DOM: Fake bank panel.
- **Auto status check (DEC-13):** when the loaded view has `pendingPayment`, call `checkPayment(id, ref)` once, then
  re-read the view. The GET itself is pure.
- Review: exactly one `createQuote` per visit (guard the StrictMode double effect with a ref); heading + `<dl>` lines +
  primary button + Back link, nothing else (no fake-bank control, no activity). Confirm button pending state with
  `aria-disabled="true"` and a click guard while in flight; focus stays (001 BUG-010).
- Outcome Notices: role="status" for pending/completed, role="alert" for failed/refused; each failed/refused outcome offers
  its next step ("Review again", "Check status", "Back").
- Fake bank panel: `<section aria-labelledby>`, heading "Fake bank (simulation control)", selects labelled "Next debit
  outcome" (`NEXT_DEBIT_OUTCOMES`) and "Next status check" (`NEXT_STATUS_CHECKS`), button "Set", current setting as text.
- Card list (DEC-11): each row gains a link "Cardholder view" with accessible name "Cardholder view for {card name}" to
  `/cardholder/{id}`.

**API (design §7):** `GET /api/cardholder/cards/{id}`; `POST /api/cardholder/cards/{id}/quotes` (201; 409 problem with
`code`, `message`, `balanceOwed`, `pendingReference?`); `POST .../payments/{reference}/confirm` (200 receipt; 409
`balance_changed | quote_refused | payment_pending`; 404); `POST .../payments/{reference}/check`; `GET .../payments/{reference}`;
`GET /api/fake-bank`; `PUT /api/fake-bank/steering`; `GET /api/cards/{id}/activity`; `GET /api/cards/{id}/payments`;
`GET /api/cards/{id}/payments/{reference}`. 409 → `ApiError` with the ProblemDetails (incl. `code`/`message`) in `problem`.

**FakeApiClient behaviour (design §15.2, §15.4):** seed gains purchases per card (amounts) and the linked account
(defaults: "Brightline Supplies Ltd current account", 7731, £25,000.00); `withBank(outcome)` sets the next debit outcome
(same wire values as the fake bank; one-shot) and `withStatusCheck('does_not_answer')`; quote → confirm → receipt with
the §17 messages; balance = purchases − completed payments; refuse above the account balance; pending blocks quotes
(W-9); a balance change between quote and confirm (e.g. `addPurchase(id, amount)`) rejects 409 balance_changed (W-6);
`hold()` works for the new methods; `calls` records method names. `getCard` returns `balanceOwed` computed the same
way. Keep the existing 001 behaviour and tests green.
