## Verdict: **CHANGES**

Counts: blocker 1 · major 2 · minor 5 · nits (one line at the end).

Most of the PR is sound. The schema matches design §6:
- `UX_Payment_OnePending` is filtered on `[State] = 'Pending'`.
- The quote PK is `Reference varchar(12)`, and the `Payment → PaymentQuote` FK has a unique `Reference`.
- `IX_Payment_Completed` includes `Amount`.
- Every FK is `Restrict`, so no cascade can delete a record.
- `LinkedAccount` holds only `LastFour`.

The model snapshot matches the model. The writer queues its changes, and `SqlCardWriter.FlushAsync` applies them in one
`SaveChanges` inside the card-lock transaction. A settlement and its events therefore commit or roll back together
(P-6, P-11). The fake bank runs in its own applock transaction, commits before it hangs, and never touches card or
payment tables. No query joins `Bank*` tables with card or payment tables (DEC-2, ADR-007).

One cross-PR seam is broken: **payment events that share a timestamp come back in random order** from SQL. PR-04
writes `ConfirmCreated` and `DebitRequested` with the same `now`, so about half of all compliance records would list
the debit request before the confirm.

## Answers to the coder's points
1. **Duplicate card names in `CreateStoreAsync`**: acceptable. Only the SQL adapter's seed needs it, and no payment contract case asserts card names. A unique default name in PR-02's `CardBuilder` would be cleaner, but that is not this PR's file.
2. **Silent seed skip**: yes, it is a misconfiguration risk. See F5: fail loudly unless the whole section is absent.
3. **`TestDataReset` with `IOptions<SeedOptions>`**: fine. It resets only the configured account, inside the one transaction, and is gated by `CardLab:TestEndpoints` (AC-37 is proven by the disabled-host test).
4. **Writer design**: atomic. Queued quote, status and settlement changes are applied after the 001 queue and saved in one `SaveChanges` before `CommitAsync`. `ChangeTracker.Clear()` in `finally` drops tracked rows from a failed unit (P-11). EF's FK ordering inserts the quote before the payment (P-6, `PayAsync`). The filtered unique index, quote PK and Payment→Quote FK match §6. No `Bank*` joins. Only the event order (F1) is wrong.
5. **Fake bank extras**: (a) timeout steering plus insufficient funds → immediate `Refused`: consistent with Flow 6 and R-15, but needs a test (F7b). (b) No request row → `NotReceived`: correct for Flow 5, but the simulated flag is wrong for steered not-received (F4, design gap). (c) A repeated reference returns the recorded outcome with steering untouched: correct per Flow 6, but needs a test (F7a). `Complete` steering plus a balance refusal marked simulated (AC-31 path) follows Flow 6 "Simulated = steering != null".
6. **Migration and snapshot**: they match the model (`has-pending-model-changes` clean). Up creates the 8 tables with the §6 types and indexes; Down drops them.
7. **Retention / records**: at schema level, every FK into the payment tables is `Restrict`, so a card cannot be deleted from under its records ("not tied to the card's life" holds by refusal rather than by cascade). No update path exists for quote shown-columns, events, ledger entries or debit requests. The only delete path is `TestDataReset`, which returns 404 when disabled (T-I-11 disabled case). Wording is stored verbatim (`RenderedLines` + `WordingVersion`); oversize text fails loudly rather than being truncated. There is no DB-level immutability (triggers or `DENY`), but the design does not require it.
