## Verdict: **CHANGES**

Counts: blocker 3 · major 1 · minor 3 · nits 2 (one line at the end).

On the doubles, the PR does what the brief asks. The in-memory store keeps copy-on-commit, rejects a second pending
payment and a second payment for a reference on commit, and floors the balance with `Money -`. FakeBank's natural
behaviour, its scripts and `FakePaymentReferences` work as specified. The PanScanner pattern is the literal seeded
number. AC-3 (P-2) and AC-31 (B-4) hold against the doubles. Tests go through the ports and assert literals, and the
stub Given/When/Then comments are kept.

**The two contract suites will not hold PR-05's SQL adapters to the design. They cannot pass on SQL at all.** Both
SQL subclasses use one `SqlTestDatabase` per test class (`SqlTestDatabase.cs:20`: "A fresh database per test
class"). PR-05 must insert fresh rows on each `Create*Async` and may not edit these suites (`PR-05.md` Harness to
use, Rules). Every test, however, reuses the same global keys:
- payment references `PAY-00000001…`: `PaymentQuote` PK, unique `Payment.Reference`, `BankDebitRequest` PK, unique
  `BankEntry.Reference`;
- the `LinkedAccount` id `1a1a…0731` from the builder default (PK).

The in-memory doubles hide this because each test gets a fresh instance. One more problem: B-6 orders 12 debits that
all carry the same `FakeClock` time, so it passes on the doubles only through a tie-break.
