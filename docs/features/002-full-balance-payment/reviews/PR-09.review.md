## DEC-5 / BUG-006 trace (tier 3)
- **Registered inside lock #1 before commit.** `_inFlight.Register(reference, completion.Task)` (`PaymentService.cs:370`) runs
  inside the `WithCardLockAsync` delegate, before `writer.FlushAsync` and `tx.CommitAsync` (`SqlCardStore.cs:83-85`).
  `WithCardLockAsync` never re-runs its delegate (no execution strategy anywhere in `src`), so `Register` runs once per confirm.
- **No leak between registration and the `try`.** If the commit fails after registration, the `catch` at `:132` calls `Fail`
  (`registered` is true). On the Create path, the code between the lock and the `try` at `:175` consists only of the pure
  conditions at `:144`, `:149` and `:154`. The `PaymentConfirmAttempt` log now runs inside the `try` (`:177`), and M12 shows
  it is still pinned.
- **Released before completion is observable.** `Complete` / `Fail` call `Release` and only then complete the task. M3 kills
  this ordering with 3 tests, including the BUG-006 disconnect test.
- **Joiners get the same outcome.** The registered task *is* `completion.Task`, so there is no wrapper any more.
  `RunContinuationsAsynchronously` is kept (`:121`).
- **Unconditional `Release` is safe.** `Register` refuses a second owner while an entry exists, and each owner releases exactly
  once (`:136`, or one of `:184` / `:188`). An old owner therefore can never remove a newer entry, which makes the removed
  `Late_cleanup_of_a_completed_registration_keeps_a_newer_entry` obsolete, as the coder says. A residual window is benign: owner A's
  lock-#1 commit fails, A's transaction rolls back, and B takes the lock and decides Create before A's `Fail` runs. B then gets an
  `InvalidOperationException` (500) with its own unit of work rolled back. No money moves and a retry succeeds. No change needed.
