## Verdict: **APPROVE WITH FIXES**

Counts: blocker 0 · major 2 · minor 4 · nits (one line at the end).

The production code is right:
- The handlers are thin. `balanceOwed` comes from `GetBalanceAsync`, with no arithmetic in the API or the SPA.
- The record endpoint returns 404 for an unknown card, a malformed reference, an unknown reference and another card's reference. Mutation M1 below confirms the test pins this.
- The admin card detail shows "Balance owed £x". The Activity table keeps the caption "Transaction history". The Payments section lists every reference with its status, state and origin badges.
- The auto status check runs once per pending reference and then refetches (DEC-13).
- The record page shows the stored wording verbatim and leaves out facts a record lacks instead of showing them as £0.00.
- The 001 E2E page object reads the 7-column Activity table and returns only rows whose Type is "Purchase", with the old six fields. I checked the specs that use it statically: `freeze`, `simulate`, `formatting`, the `a11y` first-row check and `smoke/j1` all read purchases or the first row by caption, so they still match. Nobody ran the 001 E2E suite in a browser (see Residual risk).

Both majors are about **tests that do not pin the behaviour they name**. The coder said T-I-10 and the web tests were written after the code. I checked them with mutations, and two important mutations survive:
- the AC-20 record test misses dropped wording lines, a wrong "To" account and dropped bank-outcome or confirm-attempt events;
- the "does not re-check" test passes with the once-only guard removed, which contradicts the PR body's mutation claim.
